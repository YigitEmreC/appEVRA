# CLAUDE.md

Guidance for Claude Code when working in this repository. The user-facing overview (screens, product range, live-mode setup) is in [README.md](README.md); this file covers what you need to change the code safely.

## What this is

Evra is a smart-home PWA front end for Home Assistant. It is plain HTML, CSS and ES modules: **no build step, no package.json, no bundler, no framework, no test suite, no linter.** Edit a file, reload the browser.

## Running it

- `Start Evra.bat [port]`: starts `tools/dev_server.py` (default port 8010) and opens the app in an Edge or Chrome app window.
- By hand, run `python appEVRA/tools/dev_server.py [port]` from the **parent** folder (`SMART`), then open `http://localhost:8010/appEVRA/`.
- The dev server serves the **parent directory**, not this folder, because demo mode fetches `../ha-snapshot/{home,automations,history}.json` (see `SNAPSHOT` in `js/backends/demo.js`). `ha-snapshot` is **not in this repo**. Without it, demo mode has no data.
- Port 8000 is reserved for another project of the user's. Don't use it.
- **Test hub** (`tools/test_hub/hub.py`, needs `aiohttp`): a Python stand-in for Home Assistant's auth, WebSocket and REST APIs, used to exercise **live mode** without the Raspberry Pi. It runs on :8123, has a control panel, also reads `../ha-snapshot`, and keeps state in `tools/test_hub/data/`. `Start Evra.bat` starts it minimised (`:start_hub`, skipped with `EVRA_NO_HUB=1`) with `--origin` set to the app's port; `Start test hub.bat` starts it in a visible window and opens the panel. It is a test double that covers only what the app uses.
- `python tools/make_icons.py` regenerates the PNG icons from `icons/icon.svg`.
- `Start Evra.bat` also starts the **accounts stand-in** (`tools/accounts/server.py`, :8770, stdlib only, data in git-ignored `tools/accounts/data/`). It's only used when Settings points at it; by default the app signs in with the Evra website. The **assistant** no longer runs on a computer: it is part of the Evra website's Worker (`https://evrasmarthome.com/api/assistant`, webEVRA `functions/api/assistant.js` and `lib/assistant/`). The old `../EvrAI/gemini_home_starter/server.py` is only a reference now.

- **Phone mode:** `Start Evra on phone.bat` runs `Start Evra.bat` with `EVRA_PHONE=1`.
  - The dev server then runs with `--lan` (it listens on 0.0.0.0 and adds an `X-Evra-Lan` header), and the assistant with `--lan` (`ASSISTANT_LAN=1`; it allows `http://<LAN IP>:<EVRA_APP_PORT>` as an origin).
  - Requests from other devices may only open `/appEVRA/` (not `tools/`) and `/ha-snapshot/`. Dot-paths and folder listings get 404; see `phone_may_open()` in `tools/dev_server.py`. Keep it that way: SMART also holds the Gemini key and account data.
  - The app's default `assistantUrl` is `WEBSITE_ASSISTANT` (`https://evrasmarthome.com/api/assistant`, in `util.js`). That default is never saved to settings; an old saved `...:8765` address counts as not chosen.

Live mode has **never been tested against the real Home Assistant**, only against the demo backend and the test hub.

## Architecture

```
index.html → js/main.js (shell, hash router, theme, connect())
               ├─ js/store.js        single source of truth (states + registries), pub/sub
               ├─ js/backends/demo.js  fake HA: snapshot + localStorage + automation interpreter
               ├─ js/backends/live.js  real HA: WebSocket API + REST + OAuth-style login
               ├─ js/views/*.js        one render function per screen
               └─ js/devices/cards.js  device tiles, one builder per "kind"
```

- **Routing**: hash routes `#/<view>/<params...>?query`. `VIEWS` in `main.js` lists the screens. Each view is `render(root, cleanup, ctx)`. Push teardown functions (unsubscribers, timers) onto `cleanup`; they run on the next route change. `ctx` = `{ reconnect, applyTheme, params, query }`.
- **Store** (`js/store.js`): `store.states` / `devices` / `areas` / `entities` Maps. UI subscribes with `store.watch(ids, fn)` (fires immediately and on change), `store.onRegistry(fn)` and `store.onStatus(fn)`. All of these return an unsubscribe function, which goes into `cleanup`. Backends push messages `{type: 'all'|'update'|'registry'}` into `store.apply`. Service calls go through `store.call(domain, service, target, data)`.
- **Backends share one interface**: `connect(onMessage, onStatus)`, `disconnect`, `callService`, `fetchHistory`, automation CRUD (`fetchAutomationConfig`, `saveAutomation`, `deleteAutomation`), area and device registry updates, pairing (`permitJoin`/`stopJoin`, `flowStart`/`flowSubmit`/`flowAbort`/`flowGet`, `flowProgress` (setups Home Assistant started itself for devices it discovered; ws `config_entries/flow/progress`), `flowTranslations` (the integration's texts; ws `frontend/get_translations`, category `config`), `matterCommission`), phone notifications (`pushKey`/`pushRegister`/`pushUnregister`). The Add device screen (`renderProduct` in `views/devices.js`) offers discovered devices first, and draws forms with the integration's texts, folded sections (`expandable`), progress steps and sign-in (`external`) steps. Any feature you add must be implemented in **both** `demo.js` and `live.js` (and in the test hub if live mode is to be testable). The demo mirrors HA message shapes (HA 2026.11) so views can't tell the backends apart.
- **Mode selection** (`loadSettings()` in `js/util.js`): live if served from `/local/` or `homeassistant.local`, otherwise demo. Settings are kept in localStorage key `smarthome.settings`. The demo world is persisted under `smarthome.demo.v2`.
- **DOM**: built with the hyperscript helper `h(tag, props, ...kids)` from `js/util.js`. There are no templates or innerHTML. Shared widgets (card, toggle, slider, charts, timeline) are in `js/components.js`. Icons are inline SVG via `icon(name, size)` in `js/icons.js`.

## Domain data files

- `js/catalog.js`: the 39-product Evra range of the newest product catalogue PDF (the home appliances are kinds `vacuum`, `fan`, `feeder`, `litter`, `kettle`, each with its card in `cards.js` and its entities in `demo.js` and `tools/test_hub/products.py`). Each product has `kind`, which picks the tile builder in `cards.js`, `pairing` (`zigbee|flow|matter|cloud|none`), `match`, a list of model substrings used by `productForDevice()` to recognise existing HA devices, `name` (Turkish) and `nameEn` (English, for search). `tools/test_hub/products.py` model names must stay in sync with `match`.
- `js/catalog-details.js` (`DETAILS`, keyed by product id) is **generated**: `tools/import_catalogue.py "<catalogue>.pdf"` reads the PDF with pypdf (`pip install pypdf`) and writes each product's name, category, summary, features, setup, howItWorks, examples, troubleshooting `[{problem, solution}]` and evraSays. `catalog.js` merges it into `PRODUCTS` on load. When a new catalogue comes, re-run the importer; a product name it doesn't know goes in its `NAMES` map (catalogue name → app id). The PDF's text uses private-use glyphs for digits and punctuation, mapped in `PUA_TABLE`. After that, rebuild the assistant's product data: `python tools/export_products.py` in the webEVRA repo (it writes `lib/assistant/products.js`, reading both files from `../appEVRA`), then deploy the website.
- `js/themes.js`: the colour themes (`PALETTES`, each with pastels plus dark and light surfaces) and `ACCENTS`.
- `js/config.js` (`HOME`): this specific home's entity IDs, IR remote buttons, colour presets and quick actions. When HA entities are renamed, this file is the one to update.
- `js/ideas.js`: automation idea templates. `CAPS` maps capability → catalogue products (the appliances have extra caps for their sensors: `pm25`, `foodLevel`, `litterBin`, `kettleTemp`), and `buildIdea()` produces an editor template from the home's devices. Category ids stay English; `CATEGORY_LABEL` is shown. Room names go in brackets in messages ("(Salon)"), because Turkish case endings depend on the word. An idea's actions must be ones the simple editor can show (otherwise it opens as JSON, which is dev-only): check new ones with `#/automations/new?idea=<id>`.
- `js/legal.js`: the Turkish legal texts (Gizlilik/KVKK, Kullanım koşulları, the assistant's consent text), the same as the website's `privacy.html` (AI part at `#yapay-zeka`) and `terms.html`; change both together. `openLegal(id)` shows them in a sheet (sign-in screen, Settings → Gizlilik ve koşullar). The assistant asks for consent first (`consentView` in `views/chat.js`, setting `aiConsent`); bump `AI_CONSENT_VERSION` when the consent text changes so members are asked again.
- `js/scenes.js`: the 12 built-in scenes (`DEFAULT_SCENES`) and the person's list. `SCENES` is updated in place from js/appdata.js key `scenes` (`{ v: 1, list }`, null = the built-ins), so importers see the current list; `saveScene` / `deleteScene` / `resetScenes`, `describeScene()` writes the sentence when the person didn't. The editor is `views/scene-editor.js` (`#/scenes/new`, `#/scenes/edit/<id>`); it only shows rows for kinds of device the home has. `planScene` computes the changes and `runScene` applies them; besides lights, IR TV/heater, climate, covers and the lock, scenes can set `vacuum` (`clean`/`dock`), `purifier` (`auto`/`sleep`/`max`/`off`, recognised by product `air-purifier`), `fan` (false or %) and `kettle` (product `smart-kettle`). Per-scene room choices are kept in settings, not in HA. Plugs are never touched.
- **Weather** (`js/weather.js`, Settings card `views/location-ui.js`): the place is the setting `weatherLocation` (`{ name, admin2, admin1, country, latitude, longitude, timezone }`). The app fetches Open-Meteo itself (geocoding for the search, forecast every 15 minutes, cached in localStorage `evra.weather`); WMO codes map to HA conditions in `CODES`. `outsideNow()` feeds Home's outside reading: the chosen place, else `HOME.weather`. In demo mode `backend.applyWeather(reading)` sets `weather.home` and `sun.sun` (from the place's sunrise/sunset), so weather and darkness automations follow the place. Live mode leaves HA's weather alone; Settings' "Merkezin konumunu da güncelle" calls `backend.setHomeLocation(lat, lon)` (`config/core/update`, admin only; the test hub keeps it in `Hub.core`). Show the place's times in its own `timezone`, not the device's.
- **Evra's own data** (`js/appdata.js`): `loadData(key)` / `saveData(key, value)` / `onData(key, fn)`, with a localStorage copy per mode. Backends: `getAppData` / `setAppData` (live: `frontend/get_user_data` / `frontend/set_user_data` with key `evra_<key>`, so it's per Home Assistant user; demo: localStorage `smarthome.demo.appdata`; test hub: `user_data.json`). Used for scenes and remotes.
- **Rooms** (`js/rooms.js`, Devices → Odalar): `roomBadges(areaId)` turns a room's entities (`entityArea`) into badges `{ icon, value, label, tone }` (tone '', 'on', 'warn', 'heat', 'alarm'); `roomIcon(name)` picks an icon from the room's name. The room page is `#/devices/room/<area_id>` (`renderRoom` in `views/devices.js`).
- **Remotes and IR modules** (`js/ir.js`, `js/remote-list.js`, `views/remotes.js`, `views/remote-new.js`):
  - **IR modules** are devices of catalogue kind `ir`. A module can send any code when its ESPHome firmware has Evra's `send_raw` action (`api: actions:` with `code: int[]` → `remote_transmitter.transmit_raw`, 38 kHz; see `SMART/ir-module-esphome.yaml`); Home Assistant names it `esphome.<node>_send_raw`. `irModules()` pairs modules with these actions (from `backend.listServices()`); the demo and the test hub give every IR module one.
  - **Remotes** are js/appdata.js key `remotes` (`{ v: 1, list }`, null = the built-in TV and heater remotes, which press `HOME.tv` / `HOME.heater` button entities). A database remote is `{ id, kind: 'codes', name, type, brand, set, module: <device id>, buttons: [{ k, l, p, d, s, f }] }`: `k` a standard key (`KEYS` in ir.js) or 'x' for an extra, `l` its label, `p/d/s/f` the IRDB code. `sendCode(module, code)` → `encode()` (NEC/NECx, Sony 12/15/20, RC5, RC6, JVC, Panasonic) → `esphome.<module>_send_raw`.
  - **The code database** is IRDB (`raw.githubusercontent.com/probonopd/irdb/master/codes/`, `index` then `<brand>/<folder>/<device,subdevice>.csv`), fetched on demand (the CSP allows `https:`). `buildButtons()` gives each code the key its names point to most strongly (IRDB names are messy: the same code appears as "UP" and "CHANNEL +"). Checked: LG power encodes to 0x20DF10EF, Samsung (NECx2 7,7,2) to 0xE0E040BF.
- `js/views/automation-editor.js`: `fromConfig(cfg)` / `toConfig(state)` convert between HA automation YAML/JSON and the simple editor. Configs it can't represent fall back to the JSON editor, which is dev-mode only. `stateOptions()` returns `[value, trigger label, condition label]`; vacuums, fans (speed and preset fields), enum sensors (such as the feeder's food level) and `zone.home` (people at home) are supported.

## The Home Assistant add-on (serving Evra from the Pi)

- **This repo is also the add-on repository**: `repository.yaml` at the root (Home Assistant needs it there) and the add-on in `evra/` (`config.yaml`, Dockerfile, `build.yaml` with pinned base images, nginx settings, start script, DOCS, CHANGELOG). Don't add another `config.yaml` anywhere in the repo: Home Assistant would take it for a second add-on. `config.yaml` has `image: ghcr.io/yigitemrec/{arch}-addon-evra`; the images are built by `.github/workflows/addon.yaml` (linter + test build on every push; images on a `v<version>` tag, which must match `version`).
- `python tools/build_addon.py` assembles `dist/addon/` (git-ignored) for a local test on the Pi: the add-on without the `image:` line (so the Pi builds it) plus the app files (`index.html`, `manifest.webmanifest`, `sw.js`, `css/`, `js/`, `icons/`, nothing else), LF line endings, `icon.png`/`logo.png`, and sw.js's `CACHE` stamped `-addon-<version>`. The workflow runs the same script. **Raise `version` in `evra/config.yaml` for every release.** `evra/**`, `repository.yaml` and `.github/**` are LF-only (`.gitattributes`).
- nginx serves the app on **8099** (phones, PCs, panels) and **8098** for Home Assistant's sidebar (ingress, only `172.30.32.2`). Every file is `Cache-Control: no-cache`. Both send a **Content Security Policy** (`script-src 'self'`: no inline scripts, so `index.html` loads `js/boot.js`; inline styles are allowed for the SVG scenes) plus `nosniff`, `Referrer-Policy` and `Permissions-Policy` (`evra/rootfs/etc/nginx/includes/headers.conf`). Never add inline `<script>` or `on…=` attributes.
- The start script writes **`evra-config.json`** from the add-on options: `{mode, hassUrl}` with `hassUrl` `"auto"` (this host, port 8123), `"origin"` (the sidebar version) or an address, and optionally `hassUrlHttps` (Home Assistant's internet address, used only when the page itself is `https://`, e.g. through Cloudflare Tunnel; at home and on panels Evra stays local); `assistantUrl` may be relative. `loadSiteConfig()` in `util.js` reads it before anything else (top-level `await` in `main.js`); `placeDefaults()` turns it into defaults, and `saveSettings` never saves a value equal to its default. Without the file nothing changes.
- Home Assistant needs `http: cors_allowed_origins:` with the add-on's address (the user adds it; see `evra/DOCS.md`).
- **Self-reload** (`js/updates.js`): every 10 minutes the app reads `sw.js`'s `CACHE` from the server; when it changed, it reloads when the page is hidden or untouched for 2 minutes, never while editing, chatting, in the automation editor, in the Customize panel or typing.
- **Old engines** (wall panels): `js/boot.js` (a classic script) loads `main.js` only if the browser supports modules and CSS `color-mix()`; otherwise it shows which engine it found, with a "Try anyway" button.

## The shared app and Evra homes

- **One app for every client: `https://app.evrasmarthome.com`**, a Cloudflare Worker named `appevra` with static assets (`wrangler.jsonc`: publishes only `dist/site`; build command `python3 tools/build_site.py`, deploy command `npx wrangler deploy`, root directory empty). `tools/build_site.py` copies the app files, writes the `_headers` file from the add-on's nginx settings (same CSP) and stamps sw.js's `CACHE` with the commit. No `evra-config.json` there.
- **Homes:** the website (webEVRA `lib/accounts.js`, `lib/tunnels.js`, table `evra_homes`, admin page `public/evra-evler.html`) keeps each client's home with its Home Assistant's internet address, and makes one Cloudflare tunnel + `h-xxxxxx.evrasmarthome.com` address per house through Cloudflare's API. `/me` returns `home: {id, name, url}`; any number of accounts can share a home. One tunnel per house on purpose: the same token on several Pis would make Cloudflare spread visitors between houses.
- **In the app:** `account.js` hands `memberHome()?.url` to `util.js` (`setAccountHome`, because util can't import account). `placeDefaults()` picks Home Assistant in this order: the add-on's settings file (Pi, panels: local, no internet needed), the account's home, the old defaults; a choice in Settings > Connection still wins, and defaults are never saved. `main.js` reconnects when the account's home changes. Settings > Connection says where the address comes from (`homeSource()`).
- **The accounts stand-in** (`tools/accounts/server.py`) has the same homes requests (`GET/POST /api/homes`, `PATCH/DELETE /api/homes/{id}`, `home_id` on `PATCH /api/members/{id}`), with typed-in addresses (no tunnels). **Keep the two APIs in step.**
- Each house's Home Assistant needs `cors_allowed_origins: https://app.evrasmarthome.com`, and the website's `ACCOUNTS_ORIGINS` needs it once.
- **Before leaving the app for Home Assistant's login**, `reachable()` in `live.js` posts an unknown `grant_type` to `/auth/token` (CORS-enabled, harmless): readable means `ok`; unreadable but something answers means `not-ready` (a Cloudflare tunnel error when the house's Pi is off or not set up, or `cors_allowed_origins` missing the app); nothing at all means `unreachable`. The last two stay in the app with a message and keep retrying.
- **Work only in this repository folder** (the GitHub Desktop clone). Copying an older copy of the app over it once undid committed work.

## Tunnel test (https on a real phone, without the Pi)

- `Start tunnel test.bat` builds the app, then starts the test hub (with `--origin https://evra-test.evrasmarthome.com`), `tools/tunnel_test/serve_app.py` (port 8090: **only** `dist/addon/evra/app`, the add-on's headers read from `evra/rootfs/etc/nginx/`, an `evra-config.json` with `hassUrlHttps`) and `cloudflared` (token from git-ignored `tools/tunnel_test/token.txt`, passed as `TUNNEL_TOKEN`). Steps: `tools/tunnel_test/README.md`.
- **Never tunnel `tools/dev_server.py`**: it serves the whole parent folder and trusts local requests. Requests with Cloudflare headers (`Cf-Ray`, `Cf-Connecting-Ip`) can't open the test hub's control panel.
- The website's accounts API only accepts the app from the home network or from `ACCOUNTS_ORIGINS` (webEVRA `lib/accounts.js`); internet addresses of the app must be added there.

## Notifications on phones

- `js/push.js` + the Settings → Notifications card: a device switches on notifications, the browser subscribes with the key from Home Assistant's **HTML5 Push Notifications** integration (websocket `notify/html5/appkey`) and registers at `POST /api/notify.html5` (`browser` must be `chrome` or `firefox`). Home Assistant then makes a `notify.*` entity with platform `html5` for it; `DELETE` with the same subscription removes it.
- `sw.js` shows the pushes (`push`, `notificationclick`) with Evra's icon.
- The automation editor's "send to phones" writes `notify.send_message` to every `html5` notify entity, then `notify.notify` (the Home Assistant app). `fromConfig` folds these back into one step (`isPhoneStep`).
- Each visit, once connected, `refreshPush()` re-registers the subscription (browsers drop or renew them).
- Needs a secure context: `https://` or `http://localhost`. iPhones also need Evra added to the home screen.
- Demo: no registration; `notify` calls fire `demo-push`, which `main.js` shows as a real notification when they're on.
- Test hub: `tools/test_hub/push.py` imitates the integration and sends real web pushes when `pywebpush` is installed (`python -m pip install pywebpush`); the control panel has "Send a test to Evra".

## Assistant and accounts

- **EvrAI** is the assistant's name everywhere in the app (the brand is still Evra). Its mascot is `js/mascot.js` (SVG; rings take the theme colours via `--mascot-*`; gold lock when the home has no Premium). It's the EvrAI tab's icon, the chat avatar and the small button on Home. No separate tab.
- **Household plan:** the plan belongs to the home (webEVRA `lib/household.js`); `features.ai` in /me already reflects it.
- **Hey EvrAI** (`js/wake.js`): optional continuous Web Speech recognition for the wake word, per device (setting `wakeWord`); pauses while the chat mic listens (`pauseWake`/`resumeWake`) and when the app is hidden; on the phrase it opens `#/chat` and fires `evrai-wake`.
- **Home care** (`js/home-care.js`, Settings): smart alerts are Home Assistant automations with fixed ids `evra_alert_open|battery|morning`; automatic backups use HA's `backup/config/*` WebSocket API (2025.1+), Güvence/Premium only.
- **Performance:** live mode uses `subscribe_entities` (compressed diffs, `applyCompressed` in `backends/live.js`) with a fallback to `get_states` + `state_changed`. Light mode (`util.js` `applyLite`, `:root[data-lite]`) drops blur/glass and stops the sky on slow devices; setting `lite` auto/on/off. Polls on Home skip while `document.hidden`.

- **Assistant** (`js/views/chat.js`, `js/assistant-actions.js`):
  - The app never talks to Gemini; the key is the Cloudflare Secret `GEMINI_API_KEY` of the website's Worker.
  - `chat.js` posts the question plus a **filtered snapshot** of the home (`homeContext()`: states of `SHARED_DOMAINS` with only `SHARED_ATTRS`, rooms, devices, entities, automation configs; the same in live and demo mode) to `assistantUrl` (default `https://evrasmarthome.com/api/assistant`).
  - **Never send** the Home Assistant token or address, locks, cameras, alarms, people or phone locations, or the member's name, e-mail, address or phone. The Worker filters the snapshot again, but the app is the first line.
  - **Members without the assistant** (`canUseAssistant()` false) get the Assistant tab with a lock badge (`.nav-locked` in `main.js`); tapping it opens the website's plans (`plansUrl()`, `abonelik.html`). `#/chat` shows `lockedView()`. Nothing is sent to the assistant for them: `/health` is called only from `chatView()`, i.e. when a member with the assistant opens the tab.
  - The Worker checks Premium and a monthly question limit in D1 on every request (`code`: `signin`, `no_access`, `limit`, `busy`) and returns `usage: {used, limit}`, shown in the chat header.
  - The server answers with text and **proposals**: exact actions built by its `propose_*` tools.
  - The app shows each proposal as a card. On Approve, `runProposal()` carries it out through the normal backend (`store.call`, `backend.saveAutomation`, registry updates and so on), reads the result back, and reports it to the server's `/outcome`.
  - **Evra speaks Turkish**, like the rest of the app. Card titles and details come from the assistant server, also in Turkish.
  - `#/chat?ask=<question>` (the product pages' "Evra'ya sorun" chips) puts the question in the box without sending it, then cleans the address.
  - **A new proposal kind needs both sides:** the tool in webEVRA `lib/assistant/tools.js` and its handler in `assistant-actions.js`.
  - **Read aloud** is `js/speech.js` (Web Speech API, sentence by sentence, Turkish voice for Turkish text). `chat.js` adds a Listen button per reply and the header's Read aloud switch (setting `speakReplies`). Speech stops on a new question, New chat and leaving the tab.
  - **The owner's instructions** are the Worker variable `ASSISTANT_INSTRUCTIONS`, appended to the system instruction by `systemInstruction()` in webEVRA `lib/assistant/gemini.js`.
- **Accounts** (`js/account.js`, `views/auth-gate.js`, `views/account-ui.js`):
  - **Sign in first:** `main.js` shows `renderAuthGate()` until `member()` is set (the `gated` class on `#app`), and only then builds the nav, connects the backend and routes. Signing out tears the view down, disconnects and shows the gate again. `route()` does nothing while signed out.
  - **No admin screens:** roles and assistant overrides live in the website's `evra_app_access` table, edited in the D1 Console. Don't add member management back to the app.
  - Members sign in under Settings → Evra account. The token goes in the `Authorization` header of every assistant request, and the Worker checks it directly in D1 (same sessions and `features.ai` rule as `/me`).
  - **Assistant access** is `features.ai`; admins always have it. `main.js` locks the Assistant tab with `assistantBlocked()` when a signed-in member lacks it (it opens the plans), but the real check is on the server.
  - **Base address:** `accountsUrl()`. It defaults to `WEBSITE_ACCOUNTS` (`https://evrasmarthome.com/api/accounts`), served by `lib/accounts.js` in the webEVRA repo.
    - **Website accounts:** members sign in with their website e-mail and password (the website's `users`/`sessions` tables in D1). `features.ai` comes from the Premium plan or an admin's choice. Members are added, renamed, reset and deleted only on the website.
    - **The stand-in** is `LOCAL_ACCOUNTS` (`tools/accounts/server.py`, usernames, admin-managed members). It's used only when the `accountsServer` setting points at it.
    - **Telling them apart:** `/status` and `/members` return `kind: "website"` on the website, and website members have an `email`. The UI uses that to switch labels and hide the add, reset and delete controls.
    - **Keep the two APIs in step** when either changes.
  - **The setting key is `accountsServer`**, stored only when someone chose an address. The old key `accountsUrl` was saved with every setting, so it's ignored.

## Conventions

- **Developer mode**: elements with class `dev-only` are hidden unless `<html>` has class `dev`. Technical details (entity lists, model and firmware numbers, the JSON editor, demo controls) belong behind this.
- **Theming**: light and dark through `data-theme` on `<html>` (absent means auto). All styling is in `css/app.css`, with the palette documented at its top (schemecolor "Blue Silence" / "Pale Blue and Green"). Heating is amber and alarms are red. **Use CSS tokens, never hex, for pastel colours in JS** (for example a tile `tone: 'var(--p-seawash)'`), so that colour themes recolour them.
- **Customization** (`js/custom.js`, the panel in `js/views/customize.js`, themes in `js/themes.js`): it is saved per browser in localStorage `evra.custom`.
  - **Applying the look:** `applyLook()` puts only non-default values as inline CSS variables on `<html>` (`--p-*`, surfaces, `--accent*`, `--radius*`, `--gap`, `--card-pad`, `zoom`, `--m1..3`, `--sky-op`). It also toggles layout and button classes (`ROOT_CLASSES`: for example `tiles-compact`, `btn-pill`, `qb-solid`, `depth-glow`, `press-bouncy`), which only appear when an option differs from its default, and the attributes `data-cols`, `data-sky`, `data-sky-motion` and `data-sky-tone`. `quickLook` maps a quick-action id to its own `{ tone, icon, name }` (validated in `cleanLook`).
  - **Arrangeable lists** are `{ order, hidden }`. Render them with `ordered(items, cfg)` and filter with `isHidden`, so new items appear at the end automatically. `setCustom(patch)` fires `evra-custom`, and `main.js` then re-applies the look, rebuilds the nav and header, and re-renders the current view, keeping the scroll position. Pass `{ rerender: false }` when the DOM is already updated (drags, eye toggles, CSS-only options).
- **On-screen editing** (`js/edit.js`): the palette button at the top right opens the Customize panel (Settings opens it with the `evra-customize` event and a `tab`). The panel's "Move things on the screen" fires `evra-move`, and `main.js` calls `setEditing(true)`, which adds the `editing` class and re-renders everything. While moving, the top right shows a back-to-Customize button and Done; Escape goes back to the panel. Focused items move with the arrow keys and hide with H (wired in `arrangeable`); the order list is kept on `container.editAll`, because the listeners are added once per container. While editing, renderers must also include hidden items (they show faded). Call `arrangeable(container, key, { all, locked, whole, big, flag })` on each group: its children need `data-id` (and `data-name`). `whole` means small things dragged by themselves; `big` means dragged anywhere (a finger needs press-and-hold); `flag` adds an on/off button such as the sections' `half`. It adds a grip and/or eye and saves the order with `mergeOrder`, so a container holding part of a list keeps the other items' places. Its tap-blocking only applies inside `.edit-item` elements, so buttons sharing a container (like the top-right Done) still work. `sortable()` marks the pointer event (`evraSorted`), so with nested containers the innermost one wins. Text that updates inside an arrangeable element must live in its own child node, because the handles are appended as children and `textContent =` would wipe them. To make something new movable, give it a list in `DEFAULTS` and render it through `ordered` and `arrangeable`. Tiles have their own toolbar in `home.js` (wide/small/hide). Drag-and-drop is `sortable()` in `components.js` (pointer events, mouse and touch).
- **Moving backgrounds** (`js/sky.js`, the "Moving backgrounds" part of `app.css`): there is one fixed layer behind the app, and `<html data-sky="aurora stars ...">` lists the effects to show (`EFFECTS` in `themes.js`, selected in CSS with `[data-sky~="x"]`). Themes name a mix in `PRESETS`. The `night` preset copies the Evra website's background (`webEVRA-main/public/assets/css/style.css`, `.night-sky`), and `draw` copies its showcase `.sx-lines`. Particles (snow, embers, fireflies) use a seeded scatter, so they don't jump between loads. The illustrated scenes (Istanbul, fireplace, mountains, retro horizon) are built in `js/sky-scenes.js` from shape helpers (`mosque`, `minaret`, `maidensTower`, `tongue`, `pine`, `caps`), with fills from CSS variables (`--i-*`, `--mt*`, `--f-*`) set per light/dark in the "Illustrated scenes" part of `app.css`. When appending children, spread arrays (`...lamps`), because `append()` turns an array into text. Istanbul is anchored bottom right (`xMaxYMax slice`) with a clamped height, so wide screens show the whole panorama and phones show Kız Kulesi. To add an effect: a layer in `ensureSky()`, an entry in `EFFECTS`, a line in the `data-sky~=` display list in `app.css`, and its styles. Animate only transforms and opacity, and use durations as `calc(Ns * var(--sky-slow, 1))`.
- **Motion and layout** (the "App feel" part of `app.css`): `route()` adds `view-enter` to `#view`, with `--enter-x` set from the tab order, so a new screen slides in from the side of its tab and its parts cascade in (not on an in-place re-draw). Scrolling sets `scrolled` on `<html>`, which compacts the header. On wide screens the content is one centred 1180 px column with the header padded to line up with it. Buttons press with a spring (`--spring`); the Customize press styles (`press-none`, `press-bouncy`) come later in the file and win. `prefers-reduced-motion` switches all of it off.
- **Service worker** (`sw.js`): network-first with a cache fallback. **When you add, rename or remove a JS/CSS file, update the `SHELL` list and bump `CACHE` (`evra-vN`).**
- **UI text is Turkish**: plain and friendly, addressing the user as *siz*. Comments stay in English. Numbers go through `num()` / `dec()` (Turkish decimal comma), dates and times use `'tr-TR'`, money is ₺, and search compares `fold()`ed text (Turkish lower case without accents, so "isik" finds "Işık"). Avoid case endings after a variable name (write "Pencere açık (Salon)", not "Salon'da"). Stored values and ids stay English (states, option values, category ids); only their labels are translated.
- `.bat` files must keep CRLF line endings (enforced by `.gitattributes`).
- The README sometimes refers to the folder as `app/`; the actual folder name is `appEVRA` (`dev_server.py` derives it from its own location).

## Verifying changes

There are no automated tests. Run the dev server and click through the affected screens in demo mode; **Settings → Reset demo** (dev mode) restores the snapshot. For backend or live-mode changes, also run the test hub and switch Settings → Connection to Live (`http://localhost:8123`).
